## End-to-end business flow

1. Open Live and load relevant dates, affected crew, candidate crew, roster and pairing data. Candidate completeness depends on loaded scope.
2. Find disruption through the Roster bell / Alert Center or a roster right-click Recovery action. `canRecoverViolation` admits 8004 qualification mismatches and 1001 only when a loaded ground task actually overlaps the flying pairing. 1001 takes precedence when both apply; historical 1001 pairings can be considered, unlike completed 8004 targets.
3. Select one 1001 alert and open Recovery. `visiblePlanGroups` chooses standby, swap-duty, flight-delay. Other triggers keep the older roster/standby/cross-base list; multi-alert 8004 also has Mixed. Do not assume the new methods are combined across multiple overlap alerts.
4. Generate candidates and before/after models. Hard reasons determine availability; fleet mismatch is deliberately soft. Standby has to cover pairing start and have no competing loaded task. Swap needs same business date, later start than overlapping ground-task end, two-way base/division and rank-seat matching and no other task overlap. Despite its name it exchanges whole pairings, including all duties.
5. Existing tree, method summary, All/Executable/Filtered lists, Detail, cost popup and Live before/after Preview are shared. Row highlight is browsing; checkbox chooses standby/swap for execution. Entering Flight Delay selects its one plan without a checkbox. Preview itself can also select a locally executable option.
6. Standby/swap run after-state legality preview; failures are evaluated on newly created crew/pairing tuples. Fleet-dimension 8004 becomes a warning. The retained callout SBY overlap is exempted by a time-window filter because the preview ground-row overlay cannot carry the exception marker. Flight Delay is `not-run` and can be applicable without this preview.
7. Apply rechecks that the source/target remain loaded, acquires crew/pairing locks, builds draft operations, redraws the roster and clears the visual preview. It does not save.
8. Save replays the draft operations. Confirm refresh, original-disruption resolution, replacement coverage for every segment, untouched duties, callout marker, and full ripple/KPI/legality impact. Existing new-case E2E tests stop at unsaved draft; they do not prove persisted Save and recheck closure.

Delay arithmetic: `newATD = max(groundEnd + 61min, oldATD, previousNewATA + max(0, originalGap))`; `newATA = newATD + originalBlock`. The 61-minute gap is currently a hard-coded implementation choice, not derived from a configurable rule. Example: ground ends 15:00Z; 14:50–17:45 becomes 16:01–18:56; a 45-minute turnaround moves 18:30–21:30 to 19:41–22:41. Gaps preserved does not mean legality preserved: reporting, duty/rest, time-of-day rules and later assignments can still change.

## Cost library: current behavior and findings

The dialog calls `enrichPlansWithLibraryCosts`, converts options with `optionToLibraryCostInput`, and batches `/api/recovery/calculate-cost/batch`. Backend `buildComponents` chooses type codes; the bridge selects the first stored instance per type and the latest revision, then calls the shared calculator. No selected Cost Set, recovery effective-date matching, applicability selection or FX conversion is performed in this bridge. It queries revisions per instance per option; larger candidate lists amplify database work despite the HTTP batch.

`totalCost` equals `directCost`, now the library total including decision penalties; it is not independently cash plus virtual cost. Options are resorted by cost; the tree minimum/star does not establish feasibility or pricing completeness. Cost tiers hard-code yen labels and thresholds even when amounts have another currency. The popup detects multiple currencies but the aggregate/ranking still sums raw amounts under a single currency label.

| Finding | Evidence | Consequence |
|---|---|---|
| Standby semantics incomplete | `buildComponents`: one fixed 1007 Day-off recall event; extra zero credit inputs are ignored by fixed logic | Not actual selected-crew standby/guarantee pay; a number is not pay validation |
| New swap adapter not fully integrated | frontend `isSwap` excludes swap-duty; sends changed=1 and crossRole=0; backend recognizes swap-duty and requests 1009 qty=2 | Default fixed 1009 rejects two as unpriced; separate change penalty quantity and modifier also differ from old swap |
| Delay economics absent | No delay-minute field in request; no delay component; frontend sends changed=1 while delay metrics report changed=0 | Flight Delay can get a 1015 roster-change penalty but no actual delay cost |
| Unknown prices reduce totals | null/unpriced/disabled/missing rows add nothing | Incomplete plan may look cheapest |
| Batch failure can appear as valid zero | catch per option returns directCost=0, empty breakdown, failure note | Enrichment not flagged unavailable; popup may label empty breakdown all priced |
| Currency inconsistency | totals summed raw; firstCurrency overwritten by each priced component; tiers use yen | Cross-currency ranking has no financial meaning |
| Scope-dependent stability | loaded roster groups denominator; fixed weights, nearest-follow-on heuristic; Flight Delay 100% | Not a global resilience, punctuality or legality measure |
| Adapter drops context | crossDivision inferred from mode string (none has cross-division); crossBase inferred from mode rather than actual crew bases; dhdFlightCost accepted but unused in bridge | Actual differences can be omitted or represented by unrelated modifiers |

## Save and rule-check review gaps

- The new-case E2E proves draft construction and local display only; no new Save run was authorized or needed for Help maintenance.
- `edit-flight` calls `flightService.update` repeatedly; each update uses its own DB transaction rather than the outer draft transaction handle. Whole-plan rollback across multiple flights needs a focused failure test before claiming atomicity.
- Propagation returns all affected crew/pairing IDs, but the edit-flight branch only collects reference dates. Draft-supplied affected IDs come from the one source crew/pairing; global flight references may therefore exceed notification/manday/lock scope. This is a code-review risk requiring integration reproduction, not a claimed reproduced incident.
- Fleet warnings may permit Apply, but downstream Save legality and qualification behavior must be tested independently; selectable is not operationally approved.
- The callout preview exemption is window-based, not a precise proof of ground-task identity in the engine; audit competing overlaps explicitly.

## Reuse contract for future recovery cases

Reuse `recovery-rules`/`recovery-trigger` for eligibility; `RecoveryOption` and `RecoveryPlans` for candidate shape; `visiblePlanGroups` for method selection; `RecoveryViolationDialog` for browsing, selection, Detail and Preview; `RecoveryCostBreakdownDialog` for traceable estimates; `buildRecoveryDraftPlan` for draft conversion; existing Save services for persistence. Avoid separate case-specific dialogs and direct UI-to-write shortcuts.

For each new numbered case, supply:

1. A concrete disruption and eligibility predicate, including scope/timezone and missing-data behavior.
2. Candidate generator with explicit hard rejection reasons and soft warnings, original snapshots and complete after-state.
3. A mutation contract: objects affected, retained duties, all legs and downstream dependencies, locks and rollback behavior.
4. Rule-check contract: what must clear, what may remain, precise exceptions, all affected crews/anchors; no inferred success from missing results.
5. Cost context with correct mode quantities, crew credit before/after, delay minutes, selected revisions/effective date, currency and unknown-price handling. Add mode-parity tests for every shared adapter.
6. Realistic base-to-base multi-leg fixture, candidate rejection tests, arithmetic checks, UI selection/preview/draft checks, and separate authorized Save/recheck/KPI/ripple verification.
7. Help article with case number, actual UI words, inputs, comparison, selection, mutation, success criteria and explicit limitations. Keep it lazy-loaded in Recovery after Live and before Scenario.

Recommended next engineering work: fix cost-context parity and unknown-price/FX ranking first, then validate full Save/ripple/legality closure for all three cases. These are findings for follow-up; this task does not change recovery business or pricing policy.
