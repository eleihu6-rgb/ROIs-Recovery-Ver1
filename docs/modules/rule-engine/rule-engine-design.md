# 法规引擎架构设计

## 场景分析

多个排班员同时使用 Gantt，每人可以选择不同的法规集合：

```
排班员 A（Gantt）→ 法规集合：CCAR-121 全量法规
排班员 B（Gantt）→ 法规集合：仅疲劳管理法规
排班员 C（Gantt）→ 法规集合：自定义法规组合（去掉某些告警）
```

## 核心问题：法规引擎需要什么数据？

法规检查时，引擎需要两类数据：

### 1. 法规配置（静态，不常变）

```
哪些法规启用？阈值是多少？告警还是阻断？
```

存数据库，按 `rule_set_id` 分组：

| rule_set_id | rule_code | enabled | threshold | level |
|-------------|-----------|---------|-----------|-------|
| set_A | max_fdp | true | 13h | error |
| set_A | min_rest | true | 10h | error |
| set_B | max_fdp | true | 13h | warning |
| set_B | min_rest | false | — | — |

### 2. 业务数据（动态，来自调用方传入）

```
这个机组的排班数据、航班数据、历史工时等
```

**不需要法规引擎自己去查数据库**，由调用方传入：

```
调用方（live-server）：
  "请帮我检查这个 roster 变更是否合规"
  → 传入：机组信息 + 当前排班 + 变更内容 + ruleSetId

法规引擎：
  → 加载 ruleSetId 对应的法规配置（缓存在内存）
  → 用传入的数据逐条执行法规检查
  → 返回：[{rule: 'max_fdp', pass: false, message: '超出13h限制'}]
```

          │                 │                 │

          │         │  2. 组装法规检查请求       │

## 多用户隔离

**法规引擎本身是无状态的**，隔离在调用方实现：

```
排班员 A 操作 → live-server 收到请求
  → live-server 知道 A 选了 ruleSetId = "set_A"
  → 查数据库拿到 A 操作涉及的排班数据
  → 调法规引擎: check({ ruleSetId: "set_A", data: {...} })

排班员 B 操作 → live-server 收到请求
  → live-server 知道 B 选了 ruleSetId = "set_B"
  → 查数据库拿到 B 操作涉及的排班数据
  → 调法规引擎: check({ ruleSetId: "set_B", data: {...} })
```

每次调用都是独立的，互不影响。引擎只需要：
- 缓存法规配置（按 ruleSetId 缓存，配置变更时刷新）
- 纯计算，不持有任何用户状态

## PO/RO 优化方案：约束求解（推荐）

### 传统方式 vs 约束求解

| | 传统方式（生成-检查） | 约束求解方式（推荐） |
|---|---|---|
| 流程 | 生成候选方案 → 逐个调法规检查 → 不合规丢弃 | 法规转化为约束 → 求解器只输出合规方案 |
| 法规检查 | 上万次调用 | **不需要**，求解器自动排除不合规方案 |
| 效率 | 大量无效计算 | 搜索空间被约束剪枝，高效 |
| 结果 | 不保证最优 | 可证明最优或近似最优 |
| 法规遗漏 | 可能漏检 | 约束硬编码，不会遗漏 |

### 实现方式：Google OR-Tools CP-SAT

```python
from ortools.sat.python import cp_model

model = cp_model.CpModel()

# 法规直接变成约束，而不是事后检查

# 例：最大飞行执勤期 ≤ 13小时
model.Add(duty_end[i] - duty_start[i] <= max_fdp_minutes)

# 例：最小休息时间 ≥ 10小时
model.Add(duty_start[i+1] - duty_end[i] >= min_rest_minutes)

# 例：7天内累计飞行时间 ≤ 60小时
model.Add(sum(flight_hours[d] for d in week_range) <= weekly_limit)

# 求解器自动找到满足所有约束的最优方案
solver = cp_model.CpSolver()
status = solver.Solve(model)
# 输出的方案已经 100% 合规，无需再检查
```

### 法规分类处理

| 法规类型 | 求解器中的处理方式 | 举例 |
|---------|------------------|------|
| **硬约束** | `model.Add()` — 违反则无解 | 最大 FDP、最小休息、资质要求 |
| **软约束** | 目标函数惩罚项 — 违反扣分 | 偏好基地、均衡工时 |
| **计算类** | 求解器内直接建模为变量和表达式 | 执勤期计算、工时累计 |
| **复杂业务规则** | 求解后少量验证（极少数） | 无法数学建模的特殊规则 |

### PO 优化流程（约束求解方式）

```
1. 从法规引擎获取当前航司的法规配置（一次性 HTTP 读取）
2. 将法规配置转化为 OR-Tools 约束
   - max_fdp=13h → model.Add(duty_end - duty_start <= 780)
   - min_rest=10h → model.Add(next_start - duty_end >= 600)
   - ...
3. 构建优化目标（最少环数 / 最低成本）
4. 求解器运行（法规已内嵌为约束）
5. 输出结果已 100% 合规，无需再逐条检查
```

### RO 优化流程（约束求解方式）

```
1. 从法规引擎获取法规配置（一次性 HTTP 读取）
2. 将法规 + 机组资质 + 偏好转化为约束
3. 构建优化目标（均衡工时 / 满足偏好 / 最低成本）
4. 求解器运行
5. 输出最优分配方案，已 100% 合规
```

## 最终调用架构

```
┌─────────────────────────────────────────────────────────┐
│                   法规引擎 (TypeScript + Fastify)         │
│                   端口 3001，HTTP 服务                    │
│                                                         │
│  ┌─────────────────┐  ┌──────────────────────────────┐  │
│  │ /api/check      │  │ /api/rule-config/:ruleSetId  │  │
│  │ 实时法规校验     │  │ 获取法规配置（供 PO/RO 读取） │  │
│  │ （单次/批量）    │  │                              │  │
│  └─────────────────┘  └──────────────────────────────┘  │
└────────┬──────────────────────────────┬─────────────────┘
         │                              │
         │ HTTP（实时校验）               │ HTTP（一次性读取配置）
         │                              │
         ▼                              ▼
┌─────────────────┐           ┌──────────────────┐
│ live-server      │           │ PO/RO Engine     │
│ pbs-server       │           │ (Python)         │
│                  │           │                  │
│ 排班操作时调用    │           │ 1. 读取法规配置   │
│ 批量校验接口      │           │ 2. 转化为约束     │
│                  │           │ 3. OR-Tools 求解  │
│                  │           │ 4. 输出合规方案   │
└─────────────────┘           └──────────────────┘
```

### 各调用方总结

| 调用方 | 调用方式 | 调用频率 | 说明 |
|--------|---------|---------|------|
| live-server | HTTP `/api/check` | 每次排班操作 | 实时校验，批量接口 |
| pbs-server | HTTP `/api/check` | 每次申请/交换 | 业务校验，批量接口 |
| PO engine | HTTP `/api/rule-config` | 优化开始前一次 | 读取法规配置，转化为 OR-Tools 约束 |
| RO engine | HTTP `/api/rule-config` | 优化开始前一次 | 读取法规配置，转化为 OR-Tools 约束 |

### 关键变化

- **PO/RO 不再频繁调用法规引擎**：优化前一次性读取法规配置，转化为求解器约束
- **法规引擎保持 TypeScript**：不需要改 Python，因为 PO/RO 不再紧密耦合
- **求解器输出即合规**：不需要事后逐条检查，效率大幅提升

## 关键设计要点

| 问题 | 答案 |
|------|------|
| 多用户如何隔离？ | 每次调用传 `ruleSetId`，引擎无状态 |
| 法规配置谁管理？ | 数据库存储，引擎内存缓存 |
| 业务数据谁提供？ | 调用方查库后传入，引擎不读业务数据 |
| PO/RO 如何使用法规？ | 优化前一次性读取法规配置，转化为 OR-Tools 约束 |
| 求解后需要再检查吗？ | 硬约束/软约束/计算类不需要，极少数复杂规则可能需少量验证 |
| 法规引擎用什么语言？ | TypeScript（Fastify HTTP 服务），PO/RO 无需直接 import |
