# PBS 日历操作弹层防裁切设计

> 状态：已批准并实现，待提交
> 日期：2026-07-21

## 1. 背景与问题

PBS Bid 工作台左侧 `BIDDING CALENDAR` 支持点击日期后打开 Days Off / Pairing 操作弹层。当前弹层作为 `ScheduleEventCalendar` 内部的绝对定位元素渲染，仍处于以下裁切容器之内：

- 共享工作台左侧日历 clipper 使用 `overflow-hidden`，用于日历收起动画；
- `DashboardSchedulePanel` 使用 `overflow-hidden`，用于卡片圆角和内容边界；
- 页面根工作区固定在视口内，不允许整页滚动。

第一周日期当前固定向下展开。Pairing 弹层包含搜索、pairing occurrence 列表、Tier 多选和操作按钮，内容高度大于普通 Days Off 弹层。当第一周日期向下展开时，弹层底部会越过左侧面板的可视边界，并被父容器裁切，导致底部 Tier 或操作按钮无法完整看到。

该问题是实际布局缺陷，不是浏览器缓存或数据问题。

## 2. 目标

- 日历操作弹层始终完整落在左侧工作台的可视区域内。
- 弹层继续与用户点击的日期或星期入口保持明确的空间关联。
- 可用空间不足时自动选择向上或向下展开，不再依赖固定的“第一周向下、其他周向上”规则。
- 页面、共享工作台和左侧日历卡片继续保持不滚动。
- Pairing occurrence 长列表只在弹层内部滚动。
- Days Off 与 Pairing 共用同一套定位和防裁切规则。
- 保留现有关闭、保存、禁用和焦点交互。

## 3. 非目标

- 不调整 Bid 右侧属性列表布局。
- 不恢复页面整体滚动或左侧日历滚动。
- 不改变 Days Off / Pairing 的数据结构、保存规则或 Tier 业务逻辑。
- 不修改 API、后端、数据库或 migration。
- 不重新设计弹层视觉样式或业务字段。

## 4. 方案比较

### 方案 A：压缩 Pairing 弹层固定高度

缩短 occurrence 列表或间距，使当前截图中的弹层勉强放下。

优点：改动最小。

缺点：依赖当前内容高度和视口尺寸；以后增加错误提示、文案或字段仍会再次被裁切，不能解决父容器裁切的根因。

### 方案 B：移除父容器 `overflow-hidden`

允许弹层直接越过日历卡片边界。

优点：无需移动弹层渲染位置。

缺点：会影响左侧日历收起动画、卡片圆角裁切和工作台固定视口布局；弹层即使越过卡片，也仍可能超出页面可视区域。

### 方案 C：Portal + 实际尺寸感知定位（采用）

将遮罩层和操作弹层渲染到 `ScaledPageCanvas` 已有 Portal 根节点，脱离左侧卡片的 `overflow-hidden` 裁切上下文。打开后读取锚点、弹层和左侧日历可视区域的实际尺寸，选择向上或向下展开，并把最终坐标限制在左侧可视区域内。

优点：解决根因；适配不同弹层高度、缩放比例和窗口尺寸；不破坏现有固定工作台与收起动画。

代价：需要集中管理锚点元素引用、Portal 坐标换算和尺寸变化后的重新定位。

## 5. 交互设计

### 5.1 打开与锚点

- 点击具体日期时，以该日期单元格作为锚点。
- 点击星期标题时，以对应星期标题作为锚点。
- 居中类型入口继续以左侧日历可视区域为定位上下文。
- 弹层横向优先对齐锚点中心，并始终限制在左侧日历可视区域左右边缘内。

### 5.2 垂直避让

定位时计算锚点上方和下方的可用空间：

1. 优先选择能够完整容纳弹层的一侧；
2. 上下都可容纳时，日期单元格弹层固定优先向下展开；星期标题弹层保留现有的向上展开偏好；
3. 上下都不能完整容纳时，选择空间更大的一侧；
4. 最终位置必须按统一安全间距限制在左侧可视区域顶部和底部之间；
5. 极端小窗口下，弹层设置最大可用高度；标题、日期、Tier 选项和操作按钮保持固定，occurrence 列表通过 flex / `min-height` 收缩并在内部滚动，页面本身不滚动。

定位不能依赖写死的 Pairing 弹层总高度。加载状态、错误提示、保存错误或内容尺寸变化后，需要基于真实尺寸重新计算。

### 5.3 层级与边界

- 弹层和点击空白处关闭层一起进入 `ScaledPageCanvas` Portal，避免不同裁切上下文导致关闭层和弹层不一致。
- Portal 内容恢复 `pointer-events`，Portal 根节点本身继续不截获普通页面交互。
- 弹层的水平边界是左侧 `BIDDING CALENDAR` 可视列，不允许覆盖右侧 Bid 工作区。
- 日历收起、路由切换或 action popover 关闭后，不保留过期坐标。

### 5.4 现有行为保持

- 点击弹层外空白区域仍关闭弹层。
- 保存进行中时，关闭层、Cancel、Clear、搜索和选项继续遵循现有禁用规则。
- `ADD BID`、错误信息、blocked Tier、Days Off / Pairing tab 切换和 Tier 多选逻辑不变。
- 弹层视觉样式、宽度和内部列表滚动样式保持现状。

## 6. 技术边界

### 6.1 共享组件职责

`ScheduleEventCalendar` 继续负责：

- 日期、星期和事件渲染；
- action anchor 与对应 DOM 锚点的关联；
- 调用共享定位逻辑；
- 将关闭层和弹层渲染到可用 Portal target。

定位计算应是独立、可单元测试的纯逻辑或小型共享 hook，输入至少包括：

- 锚点矩形；
- 弹层矩形；
- 左侧日历可视边界；
- 安全间距；
- 当前 anchor 类型。

输出为 Portal 坐标和最终展开方向。不要把 Bid 页面、Pairing 业务字段或特定日期写入定位逻辑。

### 6.2 缩放坐标

`ScaledPageCanvas` 使用 CSS transform 缩放。定位实现必须以 Portal 根节点的坐标系为准，将浏览器 `getBoundingClientRect()` 得到的屏幕坐标正确换算为缩放画布坐标，不能通过某个固定分辨率下的 magic number 补偿。

### 6.3 尺寸更新

以下情况需要重新定位：

- 弹层首次挂载并取得真实尺寸；
- Pairing 数据从 loading 变为成功或失败；
- 搜索、错误提示或 tab 切换造成弹层高度变化；
- 浏览器尺寸或画布缩放变化；
- 锚点或左侧日历边界发生变化。

优先复用浏览器原生测量能力，不新增第三方定位依赖。

## 7. 测试设计

### 7.1 单元与组件测试

- 下方空间足够时，弹层向下展开。
- 下方不足、上方足够时，弹层向上展开。
- 两侧都不足时，选择空间较大的一侧并限制最终边界。
- 宽弹层在最左和最右日期列仍保持在左侧日历水平边界内。
- 非 `1:1` 画布缩放时，屏幕坐标能正确换算为 Portal 坐标。
- 弹层和关闭层实际渲染在 `ScaledPageCanvas` Portal 根节点内。
- loading / error / 内容尺寸变化后重新计算位置。
- Portal 中的点击空白关闭、保存中不可关闭等行为保持。
- Days Off 和 Pairing 均使用同一定位路径。

### 7.2 Playwright 回归

在真实 PBS Bid 页面、`1920 × 1080` 视口下：

1. 点击第一周存在 Pairing 数据的日期；
2. 切换或保持在 `PAIRING` tab；
3. 验证弹层顶部、底部、Tier 选项、`Cancel` 和 `ADD BID` 全部位于左侧日历可视区域；
4. 验证弹层未进入右侧 Bid 工作区；
5. 验证页面和左侧日历没有新增滚动条；
6. 验证 occurrence 列表内容较多时仅列表内部可滚动；
7. 追加一个较矮桌面视口回归，验证自动翻转或边界限制仍有效。

### 7.3 交付门禁

- 相关 Vitest 通过；
- 相关 Playwright 通过；
- `npx tsc --noEmit` 通过；
- 根目录 `npm run check:ui` 通过且 hard violation 为 0；
- 更新对应 PBS QA 人工测试案例。

## 8. 验收标准

- 截图所示第一周日期打开 Pairing 弹层时，不再裁切任何 Tier 或操作按钮。
- 弹层在不同日期行、不同窗口高度和加载/错误状态下都完整位于左侧可视区域内。
- 弹层不会覆盖右侧工作区。
- 页面、左侧卡片和日历不出现新的整体滚动条。
- Pairing occurrence 长列表仍能在弹层内部滚动和选择。
- Days Off 与 Pairing 的保存、取消和关闭行为无回归。

## 9. 风险与控制

- **缩放坐标换算错误**：使用 Portal 根节点与实际 DOM 矩形计算，并在不同视口运行 Playwright。
- **首次测量闪动**：弹层取得有效位置前避免以错误坐标可见，完成测量后一次展示。
- **内容高度变化后再次越界**：监听实际尺寸变化并重新定位，不只在打开时计算一次。
- **关闭层层级回归**：弹层和关闭层进入同一个 Portal，并补充交互测试。
- **左侧收起动画冲突**：收起时关闭 action popover 或清理坐标，不修改 clipper 的动画职责。

## 10. Multi-Agent Parallelism Assessment

- Recommendation：No
- Rationale：共享弹层渲染、定位逻辑和回归测试紧密耦合，任务规模有限，拆分写入会增加接口与测试冲突。
- Suggested split：不拆分；主 agent 依次完成定位逻辑、组件接入、测试和 QA 文档。
- Write boundaries：`ScheduleEventCalendar` 及定位辅助代码、相关组件测试、PBS Portal Playwright、QA 文档。
- Conflict risk：低；实施时需避开工作区中无关的 Pairing Search 后端改动。
- Execution gate：本 spec 经用户审阅并明确批准后才开始实现。
