# Crew Bid 导入明细分批写入与失败批次恢复设计

## 背景

2026 年 7 月全员 Crew Bid 导入批次 `02c2f1c3-b7b1-451e-87d4-ca607200a4d9` 处理了 663 名机组。业务写入阶段已经写入 651 条 Bid，但保存导入明细时失败，最终批次状态为 `failed`。

已确认根因不是 Bid 数据校验，而是单条 PostgreSQL 语句参数过多：

- 本批次需要保存 6,092 条问题明细。
- 每条问题明细使用 12 个绑定参数，共 73,104 个参数。
- PostgreSQL 单条语句最多支持 65,535 个绑定参数。
- 实际错误中的剩余参数数 7,568，等于 `73,104 - 65,536`，与参数上限溢出完全吻合。

由于导入明细和批次汇总在同一事务中，明细写入失败后事务回滚，导致页面只能看到批次失败，无法保存 6,092 条详细原因；此前完成的 651 条 Bid 业务写入及其回滚备份仍然存在。

## 目标

1. 导入人数和问题数量较大时，完整保存所有 Import Items 与 Problems，不再触发 PostgreSQL 参数上限。
2. 保留现有事务语义：任意一批明细写入失败，整次明细事务回滚，不产生半套审计数据。
3. 增加能覆盖本次 663 人、6,092 条问题规模的回归测试。
4. 修复并验证后，回滚失败批次，删除该批次写入的 Bid，并恢复导入前数据。
5. 本次不重新导入；由用户在页面上重新执行。

## 非目标

- 不修改 Bid 的解析、映射、校验或业务写入规则。
- 不截断、采样或丢弃问题明细。
- 不把明细保存改成异步任务或独立事务。
- 不修改数据库表结构，不新增 migration。
- 不修改 Admin Tools 页面。
- 不自动执行新的导入。

## 方案选择

### 方案 A：分批写入 Import Items 和 Problems（采用）

将两类明细分别按最多 1,000 行一批写入，所有批次仍运行在当前同一个数据库事务中。

优点：

- 直接消除单条 SQL 参数上限问题。
- 所有明细完整保留。
- 不改变导入结果、事务边界和页面契约。
- 同时保护 Import Items 和 Problems，避免未来人数继续增加后再次遇到同类问题。

### 方案 B：只分批写入 Problems（不采用）

可以解决当前 6,092 条 Problems 的故障，但 Import Items 当前每行约 15 个参数，未来人数增长后仍可能触发相同上限。

### 方案 C：截断问题明细（不采用）

实现简单，但会让管理员看不到完整失败原因，也会削弱回滚和审计能力。

## 详细设计

### 分批写入

调整 `insertRunItemsAndProblems`：

1. Import Items 按原顺序切分为最多 1,000 行一批。
2. 每批执行一次 `INSERT ... RETURNING`。
3. 汇总所有返回的 Item ID，继续建立现有的 Item 唯一键到数据库 ID 的映射。
4. Problems 使用完整 Item ID 映射生成，按原顺序切分为最多 1,000 行一批写入。
5. 汇总逻辑和最终批次状态沿用现有行为。

参数规模上限：

- Import Items：约 15 个参数/行，单批最多约 15,000 个参数。
- Problems：12 个参数/行，单批最多 12,000 个参数。

两者都明显低于 PostgreSQL 的 65,535 参数上限，并为以后字段增加留出余量。

### 事务与错误处理

- 所有 Item 与 Problem 批次继续使用调用方提供的同一个数据库事务。
- 任意 Item 批次失败时，不再写入 Problems，整个事务回滚。
- 任意 Problem 批次失败时，整个事务回滚。
- 不吞掉异常，不把部分成功错误地标记为完整成功。
- 分批只改变 SQL 的组织方式，不改变记录内容、顺序、关联关系或批次统计。

## 回归测试

新增服务级回归测试：

- 构造本次故障同量级的 663 条 Import Items 和 6,092 条 Problems，验证 Problems 被拆为多条 SQL且完整写入。
- 另构造至少 1,001 条 Import Items，覆盖 Item 分批边界。
- 验证跨 Item 批次汇总的 `RETURNING` ID 映射仍然完整。
- 验证 Problem 写入被拆为多条 SQL。
- 验证 6,092 条 Problem 全部参与写入，没有截断、重复或遗漏。
- 验证 Problem 仍关联到正确的 Item ID。
- 分别模拟非首个 Item 批次、非首个 Problem 批次失败，验证异常继续抛出、调用方只执行 rollback 而不 commit，并且不会把 run 标记为完整成功。

同时运行现有 Crew Bid Import focused tests 和 `live-server` build，确认没有改变现有小批量行为。

## 失败批次回滚

代码修复和测试通过后，才允许回滚批次 `02c2f1c3-b7b1-451e-87d4-ca607200a4d9`。

### 回滚前检查

必须在 `rollbackRun` 持有的同一个数据库事务内确认并锁定相关记录，不能只依赖事务外预检查：

- 批次仍为 `failed`，没有被其他人重新处理或回滚。
- 该批次仍有 651 条回滚备份。
- 当前仍有 651 条带该批次标记的 Bid。
- 批次导入的 Bid ID 与备份记录一致。

事务内检查需锁定 run、相关 backup 和当前 Bid，确认当前 Bid 仍是该批次写入的记录，避免预检查通过后又被并发编辑或替换。除了数量、ID 和批次标记，还必须把当前 Bid 的完整业务快照与 backup 中的 `imported_snapshot_json` 做规范化比较；即使 ID 和标记未变，只要 tier、group、property、conditions 等内容发生变化，也视为用户后续修改并拒绝回滚。若任一检查发生漂移，事务回滚并停止删除，向用户报告。

当前故障批次的 651 条 backup 已确认全部缺少 `imported_snapshot_json`，原因是旧代码固定写入 `null`。因此增加两部分处理：

1. 新导入在业务 Bid 写完后读取并保存完整 `imported_snapshot_json`，后续回滚使用精确快照比较。
2. 仅对缺少导入后快照的历史批次使用严格兜底校验：当前 Bid 必须仍带本 run marker；Bid 及其 tier、group、condition、days-off、pairing occurrence 等相关记录的创建者/更新者必须仍是导入程序；所有更新时间不得晚于该 run 的完成时间。任一记录不满足即拒绝整次回滚。

历史兜底不能达到完整快照比较的同等强度，但能识别系统正常编辑流程留下的审计变化；它只用于修复前已经产生且无法补造真实导入快照的批次。

事务外仍先执行一次只读预检查用于操作确认，但它不能代替上述事务内安全校验。

### 回滚执行

调用现有 `rollbackRun` 流程，参数为：

- `confirm: true`
- `restorePrevious: true`

该流程在一个事务中：

1. 删除本批次实际写入的 Bid。
2. 对存在 `previous_snapshot_json` 的备份恢复导入前 Bid。
3. 将批次标记为 `rolled_back`。

恢复数量不要求固定等于 651：部分机组导入前可能没有 Bid。实际恢复数应等于备份中存在旧快照的数量；删除本批次写入数预计为 651。

### 回滚后验证

- 批次状态为 `rolled_back`。
- 不再存在带该批次标记的当前 Bid。
- 651 个本批次导入 Bid ID 已删除。
- 所有存在旧快照的记录已恢复。
- 此前其他成功批次写入、且不属于本批次备份范围的 Bid 保持不变。
- 不触发新的导入。

回滚测试还需覆盖“同 ID、同 marker、业务内容已被修改”的情况，并断言整个回滚被拒绝且不删除任何 Bid。

同时覆盖历史 backup 没有 `imported_snapshot_json` 的兜底路径：审计字段或更新时间发生漂移时必须拒绝回滚。

## 验收标准

- 663 Items + 6,092 Problems 的事故规模回归测试通过。
- 至少 1,001 Items 的分批边界及跨批 ID 关联测试通过。
- 后续 Item/Problem 批次失败时的事务回滚测试通过。
- 回滚遇到当前 Bid 与 `imported_snapshot_json` 不一致时会安全拒绝，不删除任何记录。
- 新导入会保存非空 `imported_snapshot_json`；历史无快照批次只有通过严格审计兜底检查才可回滚。
- Problems 不再通过单条超参数 SQL 写入。
- Import Items 和 Problems 均采用最多 1,000 行分批。
- 所有 focused tests 和 `live-server` build 通过。
- 失败批次安全回滚并通过前后数据核对。
- 用户可自行从 Admin Tools 重新发起全员导入。

## Multi-Agent Parallelism Assessment

- Recommendation: No
- Rationale: 核心修改集中在同一个服务函数及其测试，回滚又必须在修复验证后顺序执行；并行写入会增加冲突和误操作风险。
- Suggested split: 主 agent 完成代码、测试、构建、数据检查和回滚。
- Write boundaries: 仅 Crew Bid Import 服务、对应测试和本设计/实施文档。
- Conflict risk: 多 agent 同时修改同一服务测试文件时较高。
- Execution gate: 用户审阅并确认本 spec 后，才进入实施。
