# Scenario KPI Results Correction Design

Date: 2026-07-24
Scope: Scenario detail `KPI Results`, result callback KPI persistence, scenario credit aggregation

## Problem

The current scenario KPI writer still emits the previous KPI set and derives several
values from incompatible grains:

- `roster_flight` is segment-grain, while assignment counts are pairing/ground-task grain.
- optimizer assignments must be deduplicated by `pairing_id`.
- monthly credit must be attributed by each duty's own start month, not by the
  containing pairing.
- the UI currently renders database order and can omit KPI cards when a value is zero.

Scenario 679 is the reference acceptance case. Its expected Assigned breakdown is:
`FLY:145 DO:16 CRPM:1`.

## Goals

After every successful optimization result, persist exactly these eight KPI rows:

| idx | KPI | Value |
|---:|---|---|
| 1 | Crew Utilized | crew counts by rank, e.g. `FO: ... / IFD: ...` |
| 2 | Assigned | optimized FLY pairing count + CR ground counts, with breakdown |
| 3 | Highest Credit | maximum non-zero crew monthly credit |
| 4 | Avg Credit Hours | average of non-zero crew monthly credit |
| 5 | Pairing Lines | FLY pairing count with PA/optimized description |
| 6 | Reserve Lines | RES pairing count with PA/optimized description |
| 7 | Pairing Coverage | average FLY pairing coverage |
| 8 | Reserve Coverage | average RES pairing coverage |

Rows must be written even when the value is zero. The Gantt detail page must sort
cards by `idx`, independently of API/database row order.

## Data grain and source rules

### Assignment counts

- Flying assignments: filter `assignment_group = FLY`, then count distinct
  `pairing_id` per source.
- Reserve assignments: filter `assignment_group = RES`, then count distinct
  `pairing_id` per source.
- Ground assignments: filter `pairing_id IS NULL`, source `CR`, and group by
  `assignment_group`. Each ground row is one assignment.
- For the `Assigned` value:
  - FLY = distinct CR pairing ids
  - DO / other ground groups = CR ground row counts
  - PA pairings are excluded from optimizer Assigned because they are pre-assigned
    rather than optimizer-created.
- The description uses stable group order: `FLY`, `DO`, `CRPM`, then remaining
  groups alphabetically. Zero groups are omitted from the description, but the KPI
  row itself remains present.

### Crew Utilized

Use the scenario crew population and roster result, not the engine's aggregate total:

- A crew is utilized when it has at least one CR assignment, either a distinct
  pairing or a CR ground task.
- Count utilized crews grouped by their effective rank from the result/input crew
  metadata. The display format is `RANK: count / RANK: count`, stable rank order
  from the input population, followed by unknown ranks.
- The total crew population is retained for zero-result scenarios so the KPI can
  display rank groups with zero assignments when the scenario has crew metadata.

### Pairing and reserve lines

For each input/result pairing in the requested group:

- total lines = distinct pairing ids where `assignment_group = FLY` or `RES`.
- a line is `Pre-Assignment` when it is referenced by at least one PA
  `roster_flight` row and all its composition rows have `open <= 0`.
- all other lines are `Optimize`.
- Description format:
  `Pre-Assignment: <count> / Optimize: <count>`.

The classification is deliberately based on pairing-level composition completion,
not segment-row count.

### Pairing and reserve coverage

For each pairing in the requested group:

1. `plan` is the sum of non-deleted `pairing_composition.plan` rows.
2. PA coverage is the number of distinct PA `roster_flight` crew assignments for
   that pairing.
3. optimizer coverage is the number of distinct CR `roster_flight` crew
   assignments for that pairing.
4. pairing coverage is `(PA coverage + CR coverage) / plan`.

The KPI value is the arithmetic mean of the per-pairing coverage values, expressed
as a percentage with one decimal place. Pairings with no positive plan are excluded
from the denominator. PA and CR rows for the same crew/pairing are counted once.
The description reports the population:
`<covered slots> / <planned slots>`.

This same algorithm is used for RES.

## Credit source of truth

`Highest Credit` and `Avg Credit Hours` must use the monthly credit generated by the
scenario result loader and Rust `ruletool`, not a second TypeScript pairing-duty
sum. This keeps KPI output aligned with the scenario Gantt MCred display.

### Monthly attribution rule

For every pairing duty:

- use the duty's own start timestamp;
- assign all credit for that duty to the `YYYY-MM` containing that start timestamp;
- a pairing with duties in July and August contributes its first duty to July and
  its second duty to August;
- do not assign the whole pairing to the pairing start month.

The Rust ruletool input must preserve one activity contribution per duty and its
duty-start local date. Existing per-day and monthly rollups must continue to use
the same source. Add a cross-month regression case covering one pairing with duties
starting in two months.

For KPI presentation, select the scenario's optimization month (the scenario
period/report month) and read each scenario crew's monthly `credit`. Crews missing
from the monthly table are treated as zero. `0`-credit crews are excluded from
`Avg Credit Hours` and `Highest Credit` calculations.

- Highest = maximum credit among non-zero crews.
- Average = total credit / (`eligible crew count`), where eligible means
  monthly credit > 0.
- The average description must expose the formula, for example:
  `avg credited hours per crew (2026RP07) Total Credit / (148 - 13[0 Credit])`.
  The implementation should use the actual scenario period label and counts, not
  hardcoded text.

The KPI service should read the authoritative monthly result after the loader has
completed. If the result callback currently races KPI calculation against DB load,
sequence the operations or defer KPI calculation until the loader promise resolves.

## Persistence and API behavior

- Keep the existing `scenario_kpi` schema and unique key.
- Replace all old KPI rows for the scenario before inserting the eight canonical
  rows.
- Keep `type = UTILIZATION` for Crew Utilized, Assigned, Pairing Lines, Reserve
  Lines, Pairing Coverage, and Reserve Coverage.
- Keep `type = COST` for Highest Credit and Avg Credit Hours.
- Keep cache invalidation after the eight rows are committed.
- Existing admin KPI backfill must use the same computation path.

## UI behavior

`ScenarioKpiSection` must:

- sort a copy of `kpis` by numeric `idx`, with a deterministic name fallback;
- render all eight rows when status is `DONE`, including zero values;
- preserve the existing card layout and English labels;
- render the formula descriptions without truncating the longest expected text.

No UI-specific recalculation is introduced.

## Testing

### Backend unit/integration

Extend `scenario-result-service` coverage with deterministic gzip fixtures for:

- segment duplication: FLY count deduplicates pairing ids;
- CR ground breakdown: `FLY:145 / DO:16 / CRPM:1` shape;
- all eight rows are emitted in idx `1..8`, including zero values;
- rank breakdown for Crew Utilized;
- line classification from PA + composition open state;
- FLY and RES coverage with plan, PA, and CR deduplication;
- highest/average excluding zero-credit crews and formula description;
- cross-month duty attribution, including a pairing with July and August duties.

Add or extend the Rust/ruletool regression test for the same cross-month duty case
and verify the scenario monthly table output.

### UI

Extend the scenario KPI component test to assert sorting and zero-card rendering.
Add or update a Playwright scenario-detail test that opens a DONE scenario through
the real UI and verifies:

- exactly eight KPI cards;
- canonical order;
- Assigned breakdown;
- formula text on Avg Credit Hours;
- rank breakdown on Crew Utilized.

The reference scenario 679 should be used for an environment-backed acceptance run
when its current result is available.

## Risks and open decisions

1. The exact scenario period label field used in the Avg Credit formula must be
   confirmed from the scenario model/API before implementation. The calculation
   itself uses the authoritative monthly row for that period.
2. The result callback currently starts DB loading asynchronously. Implementation
   must verify the ordering so KPI reads never observe an empty/stale monthly table.
3. Existing old scenarios may have stale KPI rows. The admin backfill should be run
   for validation, but no bulk data migration is included in this change unless
   explicitly requested.
