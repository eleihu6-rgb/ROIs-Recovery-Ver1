Scenario Gantt — Design Spec
2026-06-04 · rois-ai · gantt + live-server + engine-server
"Open scenario" 按钮目前将优化结果加载到 Live Gantt 中查看。 本设计将其改造为独立的 Scenario Gantt：从 input.gz / output.gz 渲染场景数据， 支持多个场景并行打开、微调后回写 output.gz，并通过独占锁防止并发文件冲突。

Q1 已确认 独立渲染器（非复用 Live Canvas，全量加载）   Q2 已确认 Redis TTL 悲观锁   Q3 已确认 LeadIn Live flag 决定数据源策略
1 · Feature Overview
Scenario Gantt 的核心差异点 vs. Live Gantt。
📦 数据来源
从 input.gz（机组/配对/航班基础数据）和 output.gz（优化分配结果）加载， 不查询 Live 数据库，不受其他用户 Live 操作影响。
🗂 多标签并行
可同时打开多个不同场景的 Gantt（如场景 A / 场景 B 对比）， 每个场景是独立的顶部导航标签，不相互影响。
✏️ 微调 + 独占编辑
允许用户做少量分配调整（拖动重分配、增删配对），保存写回 output.gz。 同一时间只允许一个用户持有编辑锁，其他人只读查看。
✓ 无实时同步
✓ 可开多个
✓ 与 Live 完全隔离
✓ 保存 → output.gz（非数据库）
✗ 不影响 Live 排班数据
✗ 不允许并发写入
2 · Shell 多标签方案
当前 shell-store 支持 ActiveModule + openTabs。需决定 Scenario Gantt 如何扩展这套机制。
Option A · 推荐
扩展 ActiveModule 为动态类型
将 ActiveModule 从 union 字面量改为：
"live" | "scenario" | "scenario-gantt:42" | "scenario-gantt:43" | …

每个场景独占一个顶部标签，可关闭。点击 Open Scenario 添加新标签。 Shell ContentArea 遇到 scenario-gantt:* 前缀即渲染 ScenarioGanttView， 从 ID 中提取 scenarioId。
顶部标签独立
Option B
Scenario 模块内部子标签
在 Scenario 模块的顶部加一行子标签栏， 每打开一个场景 Gantt 就在 Scenario 页内添加一个子 tab。 不扩展 shell-store ActiveModule。
嵌套布局复杂
Option C
浮动窗口
每个场景 Gantt 作为可拖动的浮动覆盖层，类似于 AppDialog 但更大。 不修改 shell-store。
与现有布局冲突大
推荐 Option A：shell-store 已有完整的 openTabs / closeTab 机制， 顶部导航已支持多标签 keep-alive（visibility:hidden 隐藏非活跃标签）。 只需将 ActiveModule 从 string literal union 改为 string（或保留 union + 加 string & {}）， ContentArea 用前缀匹配渲染 ScenarioGanttView。改动最小，体验最直观。

4 · 编辑锁方案
多用户同时查看同一场景 Gantt 时，编辑冲突防护方案。
Option A · 推荐 — 显式悲观锁
点击"获取编辑锁" → 独占写入权限
用户需主动点击 "Acquire Edit Lock" 按钮， Live Server 将 editor_user + locked_at 写入 scenario 表（或内存/Redis）。 锁有 15 分钟不活跃超时（每次操作重置）。 其他用户看到 "Locked by zhang.san" 提示，只能只读查看。 锁持有者可手动释放或关闭标签时自动释放。
用户意图明确
超时自动释放
Option B — 首次写入锁
开始拖动/编辑时自动获锁
用户无需手动操作，第一次做出修改（拖动、增删）时服务器自动尝试获锁。 若获锁失败（他人已持有）则弹出 toast 提示"场景当前被 zhang.san 锁定"， 操作回滚。只读用户无任何编辑入口。
操作后才知道被锁，体验差
锁存储方案： 可在 scenario 表添加 editor_user varchar + editor_locked_at timestamp 两列（migration）， 或者用 Redis key scenario-lock:{id}（TTL=15min）。 推荐 Redis：不需要数据库 migration，TTL 自动处理超时，清理简单。
编辑锁的 3 种 UI 状态：
👁 只读模式（无锁）
工具栏显示 Viewing · Read-only， "Acquire Edit Lock" 按钮可用。 所有拖拽/修改操作均被禁用（canvas 无 pointer-events）。
✏️ 编辑模式（持有锁）
显示 ✎ Editing · You hold the lock， "Release Lock" 按钮 + 倒计时（距自动超时剩余时间）。 "Save" 按钮出现，有未保存改动时高亮。
🔒 只读（他人锁定）
显示 🔒 Locked by zhang.san + 锁定时长。 "Request Lock" 无法点击（或提示对方释放）。 所有编辑操作禁用。
5 · 微调操作范围
允许在 Scenario Gantt 中做哪些调整？以下为推荐的最小有效范围。
操作 触发方式 写回 output.gz 包含在 V1
将配对从 A 机组重分配给 B 机组 拖动 Gantt 条到另一行（与 Live Gantt 相同交互） ASSIGNMENTS 段中更新 crew_id ✓ 是
移除机组的某个配对分配 右键菜单 → Remove / Delete 键 ASSIGNMENTS 段中删除对应行 ✓ 是

修改配对航段构成 配对编辑（属于独立功能） - 超范围
V1 只写 ASSIGNMENTS 段：output.gz 的其他 section（KPI、统计等）在微调后会 与实际分配不再完全一致。保存时在文件头部写入 ## MODIFIED_AT 时间戳标记， 区分原始优化输出和手动调整版本。KPI 数据在 V1 阶段不重算，属 V2 迭代。
6 · 数据流架构
打开 Scenario Gantt 的数据加载策略由 scenario 的 LeadIn Live 标志（leadinLive）决定， 分为两条不同的加载链路。保存微调的回写链路与此无关，两条路径共用。
路径 A — LeadIn Live = ON（每次打开实时读取数据库重建 input.gz）
勾选了 LeadIn Live 的场景，打开 Gantt 时需要获取当前 Live 数据库最新状态（机组、配对、航班）， 以便在优化结果之上叠加显示最新的 live 数据。因此每次打开都调用"类似跑优化前的 export 接口"重新产生 input.gz， 再与已有 output.gz 合并渲染。input.gz 仅作为当次渲染用的临时数据，不落盘覆盖原始优化 input。

7 · 新增 / 改动 API 汇总
端点服务说明新增 / 改动
GET /api/scenario/:id/gantt-data live-server 统一入口：内部根据 leadinLive 自动走路径 A（实时刷新）或路径 B（读快照）。返回 crew列表 + pairing时段 + ASSIGNMENTS + lead-in分配 新增
POST /api/scenario/:id/refresh-input live-server 【路径 A 专用】复用 scenario-export-service，实时读 DB 产生临时 input 快照（不落盘 engine-server），仅供 gantt-data 内部使用 新增（内部）
POST /api/scenario/:id/acquire-lock live-server 尝试获取场景编辑锁，成功返回锁token；已有他人持锁则返回 409 新增
POST /api/scenario/:id/release-lock live-server 释放编辑锁（仅锁持有者可调用） 新增
GET /api/scenario/:id/lock-status live-server 查询当前锁状态（查看者轮询，30s 间隔） 新增
POST /api/scenario/:id/patch-output live-server 接收 ASSIGNMENTS patch（增删改），重建 output.gz 并上传 engine-server 新增
PUT /optimize/result/:taskId/output engine-server 接收新 output.gz 文件，覆盖 complete/ 目录中对应场景文件 新增
GET /api/scenario/:id/roster live-server 现有接口，只读复用。新 gantt-data 接口返回更完整的渲染数据 复用
GET /optimize/result/:taskId engine-server 现有接口，返回 output.gz，无需改动 复用

9 · 已确认的设计决策
三个关键决策均已确认，无遗留问题，可进入实施计划。
✅ Q1 · 独立渲染器（非复用 Live Canvas）
决策：不复用 Live Gantt Canvas。
原因：Live Canvas 是分段/分页增量加载（按视口滚动按需请求数据）， Scenario Gantt 的数据是优化结束后的完整静态集合，应一次全量加载。 两者数据加载模型根本不同，强行适配会引入复杂的 store 隔离和数据格式转换层。
方案：新建 scenario-gantt-renderer.tsx， React + absolute-positioned div bars + CSS row virtualization（仅渲染可视行窗口，非 Canvas 绘制）。 简单、可 debug、无 Canvas 绘制复杂度，交互（拖拽）用 pointer events 实现。
✅ Q2 · Redis TTL 悲观锁
决策：用 Redis key scenario:edit-lock:{scenarioId}，value = userCode，TTL = 15 min。
每次用户在编辑模式下执行操作时重置 TTL（heartbeat 机制，前端每 5min 调一次 keepalive API）。
不需要 DB migration，关闭标签/session 过期时 Redis TTL 自然到期，无需客户端主动清理。
✅ Q3 · LeadIn Live flag 决定数据源
决策：gantt-data 接口内部分两条路径（见 §6）：
  • leadinLive = 1：每次打开时调用 scenario-export-service 实时读 DB 重建临时 input 快照（不落盘）， 与 output.gz ASSIGNMENTS 合并后返回，前端显示 Live Context 标记
  • leadinLive = 0：直接读 engine-server 上的 input.gz + output.gz， 不访问 Live DB，前端显示 Snapshot 标记
两条路径对前端透明，均由 GET /api/scenario/:id/gantt-data 统一返回， 格式完全一致。
10 · 实施分阶段建议
Phase 1 — Read-only Scenario Gantt
多标签打开场景 → gantt-data API（路径 A/B）→ 独立 React 渲染器只读展示。

低风险 3-4 天
  • shell-store 扩展（动态 scenario-gantt:{id} tab）
  • ScenarioGanttView + 独立渲染器
  • gantt-data API（路径 A + B，只读）
  • LeadIn Live / Snapshot 标记显示
Phase 2 — 编辑锁 + 微调
加入编辑锁机制 → 拖拽重分配 → 保存回写 output.gz。

中风险 3-4 天
  • Redis 锁 API
  • patch-output API
  • engine-server 文件写入接口
  • 前端拖拽 delta 计算
Phase 3 — KPI 重算 + 法规检查
微调后触发法规重检 → KPI 重新计算 → 显示微调前后对比。

高复杂度 1 周+
  • 接入 rule-engine 法规检查
  • KPI delta 显示
  • 场景对比视图
