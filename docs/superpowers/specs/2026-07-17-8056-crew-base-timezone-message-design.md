# 8056 Crew Base Timezone Warning Message Design

## Context

Scenario Gantt violation hover and Alert Center display the persisted `rule_violation.message` text directly. For rule 8056, the current message is generated by the scenario legality path in `live-server/scripts/legality-recheck-core.mjs`.

Rule 8056 itself compares elapsed rest between two UTC instants. That legality calculation must remain unchanged. The requested change is only the human-readable timestamps in the warning message.

## Requirement

For Scenario rule 8056 warning messages:

- Keep all legality calculations in UTC.
- Keep persisted `start_dt` and `end_dt` as UTC instants.
- Format the two timestamps embedded in the warning `message` using the crew member's base timezone.
- Resolve the crew base timezone from the base effective at the rest gap start.
- If no crew base timezone can be resolved, fall back to UTC without failing the legality run.

Example shape:

```text
Rest between (A 2026-06-01 22:30) and (B 2026-06-02 06:00) is 7:30, which is below the required 10 RH.
```

The date/time values in that message should be local to the crew base timezone, not UTC.

## Recommended Approach

Update the scenario legality source data for 8056 so each duty row carries the crew base IANA timezone that is effective at that duty's end time. For an emitted 8056 rest gap, the previous duty end is the `gapStart`, so this gives the formatter the crew base timezone effective at the exact point requested. Then update only the 8056 message formatter to format `gapStart` and `gapEnd` in that timezone.

This is the smallest safe change because:

- The frontend already displays persisted messages consistently across hover and Alert Center.
- The calculation inputs and comparison logic stay UTC.
- No API, DTO, or DB schema changes are needed.
- No extra Gantt first-paint request is added.

## Data Flow

1. Scenario legality loads roster duties from scenario `roster_flight`.
2. The 8056 source rows include `crew_id`, duty start/end UTC epoch seconds, labels, assignment group/code, and a new optional timezone field resolved at duty end.
3. 8056 emits TSV to the Rust checker with that timezone as an extra column.
4. The checker output remains the same for calculation fields. The JS wrapper uses the timezone associated with the crew row when formatting the final message.
5. Persisted violation rows keep UTC `start_dt` / `end_dt`; only `message` text changes.

## Crew Base Timezone Resolution

Use `crew_base` as the source of truth for crew base, not `roster_flight.base`.

Resolve the base effective at `gapStart`. In the 8056 pair comparison, `gapStart` is the previous duty's end timestamp, so the source row for that previous duty should carry the timezone resolved at its duty end. When formatting a specific emitted gap, use the timezone attached to the current crew duty row that owns `gapStart`.

If the base or timezone lookup is missing, use `UTC`.

## Testing

Add or update focused tests around the 8056 message formatter / legality script behavior:

- A UTC timestamp with a non-UTC crew base timezone formats to the local base time in the message.
- The elapsed rest calculation remains unchanged.
- Missing timezone falls back to UTC.

Run the smallest relevant test set for the changed backend/script logic. If a real Scenario UI regression test already covers 8056 message text, update it; otherwise explain why a backend-level regression is the right coverage for this text-generation change.

## Out of Scope

- Changing rule 8056 legality semantics.
- Converting stored `start_dt` or `end_dt` away from UTC.
- Parsing or transforming violation messages in the frontend.
- Changing non-8056 rule messages.
- Adding new DB columns or API fields.
