# PBS QA 测试案例治理设计

日期：2026-05-08  
作者：Codex + lei  
状态：待用户确认后实施

## 背景

PBS 进入下一个模块开发前，需要新增一条长期协作规则：开发交付不能只停留在“跑过回归测试”。后续测试人员也需要能直接使用的测试案例，按功能理解前置条件、操作步骤、预期结果和边界场景。

现有规则已经要求：

- `pbs-portal` 涉及路由、认证、核心页面交互的改动必须补回归测试。
- `pbs-server` 涉及 route、auth、sync、schema 对齐的改动必须补测试。
- 仓库总则已有“新功能必须附带测试用例”的原则。

但这些规则对“测试案例”的对象不够明确，容易被理解成只补自动化测试。用户明确要求：这里的测试案例要面向后期测试人员。

## 目标

1. 只约束 PBS 相关模块，不扩大到整个 `rois-ai` 仓库。
2. 明确 PBS 开发交付包含三类验证产物：
   - 自动化测试：单元测试、组件测试、集成测试或 E2E，按改动风险选择。
   - 回归测试：运行相关已有测试，确认旧功能不坏。
   - QA 测试案例：给测试人员使用的人工测试用例文档。
3. 每个 PBS 新功能、行为变更、关键 bug 修复、性能优化或重构，只要影响可验证业务行为，都需要新增或更新 QA 测试案例。
4. QA 测试案例按功能单独成文，便于后续测试人员按模块查找和执行。

## 非目标

- 不要求非 PBS 模块立刻采用该规则。
- 不把 QA 测试案例替代自动化测试；两者用途不同。
- 不要求每个小的样式微调都写独立 QA 用例，除非它影响业务流程、可点击交互、布局可用性或测试人员需要验收。
- 不在本轮补齐历史所有 PBS 功能的 QA 用例；规则从后续开发开始执行，历史重要模块可后续按优先级补。

## 推荐方案

采用“PBS 模块规则强化 + 按功能沉淀 QA 用例文件”的方案。

### 1. 更新 PBS 协作规则

拟更新：

- `pbs-portal/AGENTS.md`
- `pbs-server/AGENTS.md`

新增规则口径：

- PBS 功能新增、行为变更、关键 bug 修复、性能优化和重构，只要影响可验证业务行为，交付时不能只说明已跑回归测试。
- 开发侧必须根据风险补充自动化测试。
- 同时必须新增或更新面向 QA 的测试案例文档。
- 如果某次改动确实不适合自动化测试，交付说明必须写明原因，并提供人工验证步骤。
- 如果某次改动确实不需要新增 QA 用例，也必须说明原因，例如只改内部注释、无行为变化的命名清理。

### 2. QA 测试案例存放位置

建议统一放在：

```text
docs/test-cases/pbs/<module>/<YYYY-MM-DD>-<feature>.md
```

示例：

```text
docs/test-cases/pbs/pairing/2026-05-08-calendar-detail-cache-recovery.md
docs/test-cases/pbs/days-off/2026-05-09-weekday-partial-conflict.md
docs/test-cases/pbs/reserve/2026-05-10-reserve-rule-create.md
```

这样测试人员可以按 PBS 模块查找，不需要从开发 spec 或对话总结里反推测试步骤。

### 3. QA 测试案例内容模板

每份测试案例建议包含：

```markdown
# <功能名称> QA 测试案例

## 适用范围

- 模块：
- 关联页面：
- 关联接口：
- 适用角色：

## 测试目标

- 验证什么业务能力：
- 防止哪些回归：

## 前置条件

- 登录账号 / 权限：
- 数据准备：
- 环境要求：

## 测试案例

| 编号 | 场景 | 操作步骤 | 预期结果 |
|------|------|----------|----------|
| TC-001 | 正常路径 | 1. ... | ... |

## 边界与异常场景

| 编号 | 场景 | 操作步骤 | 预期结果 |
|------|------|----------|----------|
| TC-E001 | ... | ... | ... |

## 回归范围

- 需要重点回归的旧功能：
- 不需要覆盖的范围：

## 开发侧验证记录

- 自动化测试：
- 回归命令：
- 手工验证：
```

### 4. 后续开发交付口径

后续每个 PBS 模块交付时，最终说明至少要交代：

- 修改了什么功能。
- 补了哪些自动化测试。
- 新增或更新了哪份 QA 测试案例。
- 跑了哪些回归命令。
- 若有测试未执行，原因是什么。

## 方案取舍

### 方案 A：只在 AGENTS 里加一句规则

优点：最快。  
缺点：测试案例格式不固定，后续测试人员查找困难。

### 方案 B：每个模块维护一个持续追加的大测试清单

优点：模块内集中。  
缺点：文件会越来越长，单次功能变更难追踪，也容易产生重复或过期内容。

### 方案 C：每个功能单独一份 QA 测试案例文件

优点：最容易追踪单次开发，测试人员可按模块和日期查找，后续也方便归档。  
缺点：文件数量会增加，需要命名规范。

推荐采用方案 C，并在 PBS 模块 `AGENTS.md` 中写入强规则。

## 验收标准

1. `pbs-portal/AGENTS.md` 明确要求 PBS Portal 改动交付必须包含自动化测试、回归测试和 QA 测试案例。
2. `pbs-server/AGENTS.md` 明确要求 PBS Server 改动交付必须包含自动化测试、回归测试和 QA 测试案例。
3. 文档中明确 QA 测试案例是给后期测试人员使用，不等同于自动化测试。
4. 文档中明确 QA 用例文件路径规范：`docs/test-cases/pbs/<module>/<YYYY-MM-DD>-<feature>.md`。
5. 后续开始新 PBS 模块开发前，先按该规则建立对应 QA 测试案例。

## 风险与控制

- 风险：开发为了赶进度只写很空的 QA 用例。  
  控制：模板必须包含前置条件、操作步骤、预期结果、边界场景和回归范围。

- 风险：QA 用例和自动化测试重复劳动。  
  控制：QA 用例描述业务验收路径，自动化测试验证代码行为；二者可以覆盖同一场景，但表达对象不同。

- 风险：每个功能一个文件导致文件数量增加。  
  控制：按模块分目录，文件名使用日期和功能名，便于筛选和归档。

## 实施顺序

1. 用户确认本设计。
2. 更新 `pbs-portal/AGENTS.md` 的测试与交付要求。
3. 更新 `pbs-server/AGENTS.md` 的测试与交付要求。
4. 后续进入下一个 PBS 模块开发时，按模块创建第一份 QA 测试案例。
