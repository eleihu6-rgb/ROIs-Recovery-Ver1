# PBS 用户 BC 生效日期规范化设计

## 1. 背景

PBS Portal 登录会读取 `pbs_user.eff_dt`，并判断账号是否已经进入有效期。

账号 `2156`、`1703`、`13376` 在开发环境中的权限、状态、密码均正常，但
`eff_dt` 为 PostgreSQL 可以表示的 BC 日期：

```text
0001-12-31 15:54:17+00 BC
```

Drizzle/JavaScript 将该值读取为 `Invalid Date`。当前认证服务随后使用 JavaScript
比较有效期，导致账号被错误判定为不可访问并返回：

```text
403 This PBS account cannot access the portal.
```

开发、SIT、UAT 的实际登录接口已分别验证，上述三个账号均返回相同的 403。
开发环境 `f8_pbs.pbs_user` 共 816 个账号，其中 612 个启用账号使用 BC
`eff_dt`，因此这不是三个账号的单点问题。

## 2. 已确认的业务决定

用户已选择方案 A：

- BC `eff_dt` 表示“很早以前已经生效”，不是一个需要保留的真实业务日期。
- PBS 侧统一将该哨兵值规范化为 `1900-01-01 00:00:00+00`。
- 不逐个查询或推断真实入职日期。
- 不只修正 `2156`、`1703`、`13376`，而是处理所有符合相同规则的
  `pbs_user` 记录。

## 3. 目标

1. 修正开发、SIT、UAT 三套 PBS schema 中现有的 BC `eff_dt`。
2. 让受影响的启用账号恢复正常登录。
3. 在 PBS 用户同步入口规范化 BC 日期，防止后续同步重新写入。
4. 保留所有正常 AD 日期；除 `eff_dt` 及其审计字段 `updated_at`、`updated_by`
   外，不修改其他账号字段。
5. 提供可重复执行、可核查的环境修正流程。

## 4. 非目标

- 不修改密码、权限、账号状态、锁定状态或 JWT `token_version`。
- 不修改 Live `users` 表中的数据。
- 不为每个账号推断真实入职日期或账号建立日期。
- 不修改 `pbs_user` 表结构。
- 不额外创建备份表或完整数据库备份。
- 不借本任务重构其他认证、同步或用户管理逻辑。

## 5. 方案比较

### 方案一：只修正现有数据

优点是最快、改动最少。缺点是将来同步源再次出现 BC 日期时会复发。

### 方案二：修正现有数据，并在同步入口规范化（采用）

当前数据立即恢复，同时保证 `sync-pbs-users` 后续不会重新写入 BC 日期。
这是满足当前目标的最小持久方案。

### 方案三：只修改认证判断

可以绕过当前登录问题，但数据库仍保留无法被 JavaScript 正常表示的日期，其他
读取 `eff_dt` 的代码仍有潜在风险，因此不采用。

## 6. 数据识别规则

只处理严格早于公元 1 年 1 月 1 日的 `eff_dt`：

```sql
eff_dt < timestamptz '0001-01-01 00:00:00+00 AD'
```

该规则只命中 BC 日期，不会误改 `1900-01-01`、`1970-01-01` 等正常历史日期。

目标值固定为：

```text
1900-01-01 00:00:00+00
```

该常量属于本次已确认的数据兼容规则，不代表真实入职日期。

实施预检确认开发环境的 Live `users.eff_dt` 实际为
`timestamp without time zone`，目标 `pbs_user.eff_dt` 为 `timestamp with time zone`；
重叠的 `admin` 账号证明当前数据按 UTC 墙钟时间对齐。同步源查询必须按源列实际类型使用
同型 BC/AD literal 和 CASE，目标写入事务必须显式设置 `TimeZone=UTC`。目标 PBS 列若
不是 `timestamp with time zone` 则立即停止，不允许隐式适配其他目标类型。

## 7. 现有数据修正设计

### 7.1 执行工具

新增一个 PBS 管理脚本，复用现有 PBS 数据库连接和 schema 配置。脚本只允许操作
经过配置校验的目标 PBS schema，并提供两种模式：

- 默认模式：只读统计，不写数据库。
- `--apply --expected-count <N>`：在单个事务内执行规范化并完成提交前校验；
  `N` 必须等于该环境刚刚执行默认模式得到的 BC 数量。

脚本不得输出数据库密码、连接串或密码哈希。

脚本只接受以下固定环境/schema 组合，不接受任意 schema：

| 环境 | 目标 schema |
|---|---|
| development | `f8_pbs` |
| sit | `f8_sit_pbs` |
| uat | `f8_uat_pbs` |

执行前必须校验 `current_database()`、`current_user`、目标 schema、`pbs_user` 表、
`eff_dt` 列类型和角色权限。实际身份与所选环境不匹配时立即停止。

### 7.2 单环境事务

每个环境独立执行以下流程：

1. 在目标 PBS 写入所使用的同一个数据库连接上开启显式事务，并获取本功能专用的
   transaction-level `pg_advisory_xact_lock`；同步脚本使用相同的锁。
2. 在事务内查询 BC 记录总数、启用账号数、已知账号当前值，并断言总数等于
   `--expected-count`。
3. 检查 `pbs_user` 上的 UPDATE trigger；存在未纳入验证的 trigger 时停止。
4. 创建 `ON COMMIT DROP` 的事务级临时校验快照。快照只用于提交前比较，不输出
   密码哈希，也不会在提交后保留。
5. 将所有 BC `eff_dt` 更新为 `1900-01-01 00:00:00+00`。
6. 同时更新 `updated_at = now()` 和固定的审计来源
   `updated_by = 'pbs-eff-date-normalization'`。
7. 在事务内验证：
   - BC `eff_dt` 剩余数量为 0；
   - 实际更新数等于事务开始前统计数；
   - `2156`、`1703`、`13376` 若存在，日期均已规范化；
   - 除 `eff_dt`、`updated_at`、`updated_by` 外，快照中的所有字段均未改变。
8. 任一断言失败则回滚；全部通过才提交。
9. 提交后重新执行只读检查，确认 BC 数量仍为 0。

脚本应保持幂等：同一环境再次执行时，更新数量必须为 0。

用户已确认所有 BC 值均按同一个“很早以前已生效”哨兵语义处理，因此原始 BC
时间值会在提交后被有意丢弃，不建立永久备份，也不支持恢复每条记录原来的 BC
时分秒。事务提交前仍可完整回滚。

### 7.3 环境顺序

整体发布和执行顺序为：

1. 先发布带 BC 规范化和 advisory lock 的新版 `sync-pbs-users`。
2. 确认所有旧版同步实例已经结束，并暂停定时触发或排空同步任务。
3. 依次修正存量数据并逐环境验收：

   1. 开发：`f8_pbs`
   2. SIT：`f8_sit_pbs`
   3. UAT：`f8_uat_pbs`

4. 每个环境完成后实际运行一次新版同步，再次确认 BC 数量为 0。
5. 全部通过后恢复定时同步。

前一个环境未通过时，不进入下一个环境。

三个 schema 当前位于同一 `rois` PostgreSQL 实例中，但仍必须使用各环境自身配置的
角色和 schema 执行，不能使用开发角色跨 schema 越权修改。

## 8. 同步防复发设计

PBS 用户投影由 `sync-pbs-users` 从 Live `users` 同步。当前同步逻辑原样复制
`eff_dt`，因此需要在同步边界加入规范化。

仓库写入入口核查必须作为实施前置门禁。当前代码检索结果显示，
`sync-pbs-users` 是唯一会在运行时 insert/update `pbs_user.eff_dt` 的代码路径；认证
服务只读取该字段。实施时必须再次通过代码检索和 GitNexus 验证这一结论。若发现其他
写入入口，必须复用同一规范化规则或在实施前回到本 spec 补充设计。运维人员绕过应用
直接执行 SQL 不属于应用可自动防止的范围。

设计要求：

- 源查询在 PostgreSQL 中判断日期是否为 BC。
- BC `eff_dt` 在离开数据库前即转换为 `1900-01-01 00:00:00+00`。
- 正常 `eff_dt` 原样保留。
- `exp_dt` 不在本次修改范围内。
- 同步的 insert 和 update 使用相同的规范化结果。
- 不在 JavaScript 中先构造 BC `Date`，避免再次产生 `Invalid Date`。
- 同步必须在执行目标 PBS UPSERT 的同一个数据库连接、同一个显式事务中获取
  transaction-level `pg_advisory_xact_lock`。锁从读取规范化结果前开始持有，覆盖到
  最终 UPSERT/停用/派生字段更新结束，并在事务提交或回滚时自动释放。
- 管理脚本与同步脚本使用由固定 namespace 加目标 schema 生成的同一确定性锁 key，
  不允许使用进程随机值。
- 两个入口都设置有限的 PostgreSQL `lock_timeout`；超时后必须回滚并报告环境/schema，
  禁止无限等待，也不得绕过锁继续写入。

日期规范化应在数据库查询表达式中完成，而不是依赖字符串格式或本机时区。
管理脚本与同步脚本必须复用同一个 BC 边界和目标日期定义，不能各自维护两份常量。

## 9. 错误处理与安全约束

- 目标 schema、数据库连接或权限不正确时立即停止，不尝试切换到其他账号。
- 默认模式 BC 数量为 0 时视为“无需修改”并成功退出；`--apply` 的实际数量与
  `--expected-count` 不一致时回滚；数量非零但未显式传入 expected count 时拒绝写入。
- 数据修正必须使用参数化值和受校验的 schema 标识符。
- 不记录密码哈希、JWT、数据库密码或完整连接串。
- 不创建永久备份表；安全性由事务临时快照、提交前字段比较、逐环境执行和幂等条件保证。
- 执行结果只报告环境、目标 schema、扫描数、更新数、剩余 BC 数和验证结论。

## 10. 测试设计

### 10.1 同步单元测试

增加以下覆盖：

1. BC `eff_dt` 被映射为 `1900-01-01 00:00:00+00`。
2. 正常 AD `eff_dt` 保持不变。
3. `exp_dt` 保持不变。
4. insert 和 conflict update 均使用规范化值。
5. 已有 PBS 管理员跳过、缺失 crew id、字段对齐测试继续通过。
6. 实际 PostgreSQL 驱动读取数据库 CASE 结果后，得到有效的
   `1900-01-01T00:00:00.000Z`，而不是 `Invalid Date`。
7. 真实 PostgreSQL/驱动边界用例明确覆盖：
   - `0001-12-31 ... BC` 被规范化；
   - `0001-01-01 00:00:00+00 AD` 保持不变；
   - `1900-01-01 00:00:00+00` 保持不变；
   - 断言依据 `timestamptz` 绝对时刻，不依赖 session timezone 的显示字符串。

### 10.2 管理脚本测试

覆盖：

1. 默认模式不执行 UPDATE。
2. `--apply` 只更新 BC 日期。
3. 第二次执行更新数为 0。
4. 校验失败时事务回滚。
5. 非法 schema 标识符被拒绝。
6. 数据库、角色、schema、列类型或 trigger 预检不符时拒绝执行。
7. transaction-level advisory lock 能阻止同步与规范化脚本并发写入，在提交/回滚后
   自动释放，并在达到 `lock_timeout` 时回滚失败。
8. 受保护字段在提交前比较中发生变化时回滚。

### 10.3 动态 SQL 验证

同步和管理脚本包含动态 schema SQL，必须遵循项目的 generated SQL 安全标准：

- 运行 SQL 结构/fixture 测试；
- 在远端 PostgreSQL 对查询执行只读 `EXPLAIN` 或最小只读执行；
- 对管理脚本先运行默认只读模式；
- 不得静默跳过连接、权限或 SQL 验证失败。

### 10.4 PBS 人工 QA 文档

在 `docs/test-cases/pbs/auth/` 下新增本任务的人工测试用例，至少覆盖：

1. 三个环境的默认只读统计。
2. 带 expected count 的规范化执行。
3. 受影响账号 HTTP 200 登录、有效会话和身份匹配。
4. 原正常 AD 日期账号不受影响。
5. 新版用户同步执行后 BC 数仍为 0。
6. 第二次规范化执行更新数为 0。
7. advisory lock 超时失败路径不产生部分写入。

## 11. 环境验收

每个环境完成数据修正后验证：

1. BC `eff_dt` 数量为 0。
2. 执行前断言 `2156`、`1703`、`13376` 在该环境中存在；如果环境数据确实不包含
   某个账号，则记录该事实，并改为验证该环境实际存在的已知账号及另外至少一个受影响
   的启用账号。
3. 被验证账号的 `eff_dt` 为 `1900-01-01 00:00:00+00`。
4. 被验证账号使用正确密码登录返回 HTTP 200，获得有效 JWT/会话，并且会话中的
   `userCode`/员工身份与登录账号一致。401、403、500 或其他状态均视为失败。
5. 选择至少一个原本具有正常日期的账号，确认仍可正常登录。
6. 实际执行一次新版用户同步，确认不会重新产生 BC 日期。
7. 再次运行规范化脚本，更新数量为 0。

如果某个账号仍无法登录，应根据新的 HTTP 状态继续排查密码、锁定或权限；不得把所有
登录失败继续归因于日期。

## 12. 验收标准

- 三个目标 schema 中不存在 BC `pbs_user.eff_dt`。
- 三个已知账号（或按环境前置检查确认的替代受影响账号）在开发、SIT、UAT 均能
  HTTP 200 登录并获得身份正确的有效会话。
- 同步入口能够稳定将 BC `eff_dt` 转换为 `1900-01-01`。
- 正常日期、密码、权限和 PBS 安全字段不被修改。
- 自动化测试、远端 SQL 验证和逐环境登录验证均有明确 PASS 结果。
- 所有修改均未在未获用户明确命令时提交 Git。

## 13. Multi-Agent Parallelism Assessment

- Recommendation：No
- Rationale：管理脚本、同步映射与测试共享同一日期契约，工作量有限且依赖顺序明确；
  并行编辑会增加契约漂移和文件冲突风险。
- Suggested split：不拆分，由单一实现者完成代码、测试和三环境执行。
- Write boundaries：仅限 PBS 用户同步、对应管理脚本、测试和本任务文档。
- Conflict risk：低；但执行数据库修正必须严格串行。
- Execution gate：用户审核并明确批准本 spec 后，才编写实施计划和修改代码/数据。
