# Design: Batch spawn for rules 7505 / 7507 / 7305

**Date:** 2026-08-18
**Status:** Approved for implementation (pending plan)
**Scope:** `live-server/scripts/legality-recheck-core.mjs` (7505 / 7507 / 7305), `rule-engine-rs` `check-7305` (`--per-crew-window` flag), parity + timing verification.

## Problem

Live recheck spawns one `check-*` process per (crew × month × instance) for the days-off and consecutive-duty rules:

- `rule7505` / `rule7507` (legality-recheck-core.mjs L1271-1306 / L1539-1573): loop `instance → crew → month`, one `invokeRunBin('check-7505'|'check-7507', ...)` per crew per month. Pilot workset 103 → ~282 spawns (7505 ≈ 8.1s), Cabin workset 637 → ~637 spawns (7507 ≈ 7.6s).
- `rule7305` (L1399-1434): loop `crew` (all instances' `params` are fed into every spawn), one spawn per crew, plus an O(crew × lines) `qualLines.filter(...)` / `teamLines.filter(...)` scan per crew. Cabin workset 637 → 7305 ≈ 8.9s.

`MAX_CONCURRENT_BINS = 8` (L262) serializes these spawns; the per-spawn process + temp-file overhead dominates when there are hundreds of single-crew spawns.

## Goal

Batch each rule so the number of kernel spawns is proportional to distinct (instance × month × offset-group) / instance counts instead of crew counts, keeping **byte-identical output rows in the same order** as today (so `rule_violation.id` identity sequence and every persisted field are unchanged).

- 7505 / 7507: ~282 / ~637 spawns → ≈ distinct (instance × month × base-offset) groups (typically single digits).
- 7305: crew-count spawns → one spawn total (all crews, all instances).

## Non-goals

- No change to rule logic, matching, continuity, PA handling, or any kernel semantics for existing callers.
- No change to the `R` rule rows, `A`/`D` activity rows, `Q` qualification rows, `T` team rows, or `G` group rows content.
- No Rust change for 7505 / 7507 (offset is grouped in JS; single `--offset` per spawn preserved).
- No change to `runBin` / `MAX_CONCURRENT_BINS` / `assertFresh` / temp-file feeding mechanics.

## Background / constraints confirmed

- `check-7505` / `check-7507` / `check-7305` already parse **all crews** present in stdin (`by_crew` map / `duties` map) and evaluate each independently — batching many crews into one input is native.
- 7505 / 7507 require a single `--offset` per invocation (`crewLocalRpWindowUtc`), so crews are grouped by **base offset**; all crews sharing an offset share the identical RP window → byte-identical evaluation.
- 7305's `C` window is used only by `crew_scope_matches` (rule7305.rs L134-142) with the checked window days. Today the JS passes a **per-crew** window = `[min(duty start_utc), max(duty duty_end_utc)]` (L1400-1404). A single global `C` window would change scope matching for crews whose B/R/F/P qual or team eff/exp expires inside the window → **not byte-identical**. Hence a flag-gated kernel change is required for 7305 batching.
- Downstream: `applyRulesetSeverity` (L247) mutates in place and preserves order; `live-legality.mjs` persists rows in array order (L1194-1200) into `rule_violation` whose `id` is `GENERATED ALWAYS AS IDENTITY` → insertion order decides the `id` sequence. Output order must therefore be reproduced to keep the persisted table byte-identical.

## Design

### 1. Shared helper (7505 / 7507)

Add a small helper in `legality-recheck-core.mjs`:

```js
// returns Map<offsetMin, { crews: Map<crewId, rows>, window: {startUtcSec, endUtcSec} }>
// for one (instance, month): only crews that have an anchorRow for the month's local RP
// window are included; crews without an anchor are excluded exactly as today.
```

- `offsetMin = offsets.get(crewId) ?? DEFAULT_OFFSET_MIN`
- window from `crewLocalRpWindowUtc(month.rpFrom, month.rpTo, offsetMin)`
- keep `pickDaysOffAnchor(rows, startUtcSec, endUtcSec)`; skip crews with no anchor.

### 2. rule7505 / rule7507 — offset-grouped batching (JS only)

Replace the inner `for crew → for month → spawn` with `for month → for offsetGroup → spawn`:

1. Build the offset groups for the month (helper above), retaining `anchorByCrew` per group for output mapping.
2. One spawn per group: args unchanged (`--rp-start`, `--rp-end`, `--offset`, `--do-start-min`, `--emit-tsv`); stdin = all `R` lines + all grouped crews' `Q` lines + all grouped crews' `T` lines + all grouped crews' `A` lines.
3. `A` lines per crew are built exactly as today (same field mapping); just concatenated across the group.
4. Output mapping unchanged per row: `pairing_id = daysOffAnchorPairingId(anchorByCrew.get(crew))`, `matchedRule`, `start_dt/end_dt`, `calendarRpDisplayWindow`, message.
5. Order preservation: the kernel may iterate `by_crew` in a non-deterministic order (HashMap), so do **not** rely on a single emission counter. Instead, bucket the emitted rows by the emitted fields themselves — for 7505/7507 each row carries `crew` + `rpS/rpE` (window start uniquely identifies the month for that crew). Re-emit buckets in legacy order: `instanceIndex` (index in `validInstances`) → `crewAppearanceIndex` (insertion index in `assignmentsByCrew`) → `monthIndex`; within a (crew, month) bucket preserve kernel emission order (deterministic: the kernel sorts a crew's own rows).

### 3. rule7305 — instance-batched with `--per-crew-window` (JS + flag-gated Rust)

**Rust (`check-7305`):**
- Parse `--per-crew-window` from args.
- When set: do not require the global `C` row; for each crew derive `checked_start = min(duty.start_utc)`, `checked_end = max(duty.duty_end_utc)` over that crew's own `D` rows; skip crews with no duties. Pass the per-crew window into `check_rule7305_row`.
- When unset (default): current behavior unchanged — `C` required (error if missing), single global window for all crews.

**JS (`rule7305`):**
- Remove the per-crew loop and the per-crew `qualLines`/`teamLines` filters.
- **One spawn total** (today's `params` already accumulates R rows across all instances, so a single input covers every instance): args `['--emit-tsv', '--per-crew-window']`; stdin = all `R` rows + **all** `Q` rows + **all** `T` rows + `G` rows + **all** `D` rows.
- Output mapping unchanged (`rowIndex → params`, `crew_id`, `pairing_id`, severity, unit, message).
- Order preservation: bucket emitted rows by `crew_id` (each row carries it); re-emit buckets in legacy order = `crewAppearanceIndex` (insertion index in `byCrew`); within a crew bucket preserve kernel emission order (deterministic per-crew sort).

### 4. Expected impact

| Rule | Today (workset 103/637) | After |
|------|--------------------------|-------|
| 7505 | ~282 spawns, ≈8.1s | ≈ offset groups, <1s |
| 7507 | ~637 spawns, ≈7.6s | ≈ offset groups, <1s |
| 7305 | ~637 spawns, ≈8.9s | 1 spawn total, <1s (plus O(crew×lines) filter scan removed) |

Timing will be re-measured with `RECHECK_PROFILE=1` (see Verification).

## Risks

- **Output order**: mitigated by the deterministic sort keys; parity script asserts deep equality including order.
- **7305 kernel change**: gated by `--per-crew-window`; default path and other callers unaffected (only callers are this core + its tests; verified by grep). `cargo test` + binary tests cover the default path; parity covers the flag path.
- **Very large single inputs** (all crews' `D`/`A` rows in one stdin): same total bytes as today, kernel iteration is linear per crew; expected fine at 3000+ rows (already exercised by C++ semantics).
- **Version state**: runtime versions are bumped by module `dev`/`build` scripts (`live-server/version.tmp`); confirm whether the recheck scripts surface a version that needs bumping during implementation.
