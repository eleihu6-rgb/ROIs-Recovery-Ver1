# Roster Flight Source PA/MA/CR Design

Date: 2026-07-15

## Goal

Normalize `roster_flight.source` to exactly three business source types:

- `PA`: pre-assignment imported from connector-server interfaces or file imports.
- `MA`: manual assignment created in Live/Scenario Gantt, including drag/manual assign and bulk-created Gantt duties.
- `CR`: computer result generated by RO/PO/PBS optimization.

Add database comments and check constraints so live and scenario roster rows cannot drift back to legacy values.

## Current Findings

- `sql/schema/live/02-crew-roster.sql` and `sql/schema/scenario/01-scenario-tables.sql` define `roster_flight.source varchar(12)` with stale inline text `MANUAL/PBS/OPT`, no column comment, and no check constraint.
- Connector F8 transform and live inbound workers currently produce/write `source='F8'`.
- Live manual write paths currently produce `source='MANUAL'`:
  - `live-server/src/services/roster/roster-service.ts` `assignFlight`
  - `live-server/src/services/roster/roster-service.ts` `createGroundTask`
  - `live-server/src/services/roster/roster-service.ts` `assignPairing` inherits `pairing.source`, so manual pairing assignment may become `F8` or `MANUAL` instead of `MA`.
- RES Pairing Creator creates `pairing.source='MANUAL'`; any later roster rows created from those pairings must still be `MA`.
- Scenario result loader already preserves optimizer output semantics as `CR` vs `leadin` in `scenario.roster_flight`; `leadin` is a UI/data-source concept and is not valid for the new DB constraint unless mapped to `PA` or excluded from constrained rows.
- Scenario publish currently writes live `roster_flight.source='SCENARIO'`; under the new model this should be `CR`.
- PBS solver output already uses `PA` for original/pre-assigned tasks and `CR` for solver-created tasks in `pbs-engine/ColumnModelSolver_python/io/result_converter.py`.
- Legacy RO converter writes/deletes `source='OPT'`; if this path can still run, it must become `CR`.
- Gantt already visually treats scenario optimizer rows as `source === 'CR'` for the flash badge, so `CR` is an existing frontend convention.

## Proposed Implementation

### Database

Add a migration rather than editing historical schema as the operational change:

1. Backfill existing values in live `roster_flight`:
   - `F8`, `IMPORT`, connector-created rows (`created_by in ('F8_IMPORT','F8_IMPORT_GND')`) -> `PA`
   - `MANUAL`, `SCENARIO` manual/draft-created rows where appropriate -> `MA` or `CR` based on write path; existing `SCENARIO` rows should be reviewed/backfilled to `CR` if they came from scenario publish.
   - `OPT`, `PBS`, `PO`, `RO`, `CR` optimizer output -> `CR`
   - existing `PA`/`MA`/`CR` stay unchanged.
2. Backfill scenario `roster_flight`:
   - `CR` stays `CR`
   - `leadin` should become `PA` if stored as carried pre-assignment; frontend can still derive a lead-in display flag from scenario context if needed.
3. Add column comments to both live and scenario:
   - `PA=Pre-assignment/imported from external interface or file; MA=manual assignment from Gantt; CR=computer-generated optimizer result`
4. Add check constraints to both live and scenario:
   - `source is null or source in ('PA','MA','CR')`
   - Keep nullable. If nullable source data later causes a concrete integrity problem, fix the source write path immediately instead of masking it with a default.

### Connector / Import

- Change `connector-server` F8 roster transform records from `F8` to `PA`.
- Change live inbound worker idempotency deletes from `source='F8'` to an import-owned predicate such as `source='PA' and created_by in ('F8_IMPORT','F8_IMPORT_GND')`, so imported rows can be replaced without deleting manual PA-like rows if any exist later.
- Update import job TypeScript comments/tests from `'F8'` to `'PA'`.
- Leave `pairing.source='F8'` unchanged unless a separate pairing-source normalization is requested; this task is scoped to `roster_flight.source`.

### Live / Gantt Manual Assignment

- In `assignPairing`, explicitly write `source: 'MA'` for roster rows, instead of inheriting `pairing.source`.
- In `assignFlight`, write `source: 'MA'`.
- In `createGroundTask`, write `source: 'MA'`.
- In any draft replay path that calls these methods, no extra mapping should be needed because the service methods become authoritative.
- Update Live tests expecting `MANUAL`.

### Scenario / Optimizer Output

- Scenario result loader should store only `PA`/`CR` in `scenario.roster_flight.source`.
  - Optimizer-created rows remain `CR`.
  - Solver-carried lead-in/pre-assignment rows become `PA`.
  - Scenario rows are not all `CR`: any row carried from Live, including LeadIn/pre-assignment, is `PA`.
- Scenario publish to live should write `source='CR'`.
- Legacy RO converter should replace `OPT` delete/insert predicates with `CR` if still in active use; otherwise document it as out of current F8 delivery scope.

### Frontend Types

- Introduce or reuse a narrow union where practical:
  - `type RosterSource = 'PA' | 'MA' | 'CR'`
- Keep public DTO fields nullable while the DB column remains nullable.
- Scenario Gantt should expose the database value directly. Do not translate `PA` to `leadin` in frontend DTOs.

## Test Plan

- live-server focused tests:
  - roster service assign pairing/flight/ground task asserts `MA`.
  - roster inbound worker asserts imported flying rows are `PA`.
  - roster ground inbound worker asserts imported ground/single-leg rows are `PA` and idempotency delete still only removes import-owned rows.
  - scenario publish asserts live rows are `CR`.
  - scenario result loader asserts scenario rows are constrained to `PA`/`CR`.
- connector-server transform tests:
  - F8 roster and roster-ground transforms emit `PA`.
- SQL/migration validation:
  - apply migration to a test schema with legacy values and verify no non-null source outside `PA/MA/CR`.
- Gantt Playwright coverage:
  - drive a real Live manual assignment or ground-task creation and verify the returned/visible roster item is saved with `MA` via backend/test hook.
  - drive/open a Scenario optimized result and verify optimizer rows still render the existing `CR` flash indicator while pre-assignment rows do not.
- UI standard:
  - run `npm run check:ui` only if frontend UI/style files change.

## Confirmed Decisions

1. `roster_flight.source` remains nullable.
2. Scenario rows are not blindly `CR`; rows carried from Live, including LeadIn/pre-assignment, are `PA`.
3. Pre-assignment is stored as `PA`; the frontend displays the stored source value directly and does not translate it.
