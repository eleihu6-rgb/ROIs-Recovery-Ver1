Crew App · Trip Details — redesign for review (Ver1)

Five changes proposed: (1) pair STD↔STA, ETD↔ETA, ATD↔ATA in a compact 2-row matrix (three pair columns); (2) add duty-level FDP · DP · Block · Rest; (3) move the iPhone Calendar control out of the right column into a slim full-width strip; (4) use one consistent flight title for every flight, however many flights a duty/pairing has; (5) move crew markers (wake-up / leave home / report) onto the duty card so later flights no longer repeat empty “—” rows. Frames are drawn at true point size and scaled.

Theme
1 · Related times, paired

STD/STA, ETD/ETA and ATD/ATA are three pair columns; DEP and ARR stack inside each column. Two text rows instead of three full-width rows, so a duty with six sectors stays scannable. Block time is a chip in the flight header.

2 · Duty-level totals

FDP · DP · Block · Rest per duty. The portal capture already receives dutyFdp, dutyDp, dutyRestHours and fdpHours/dpHours/blhHours — they are currently thrown away.

3 · Calendar repositioned

No longer a card in the right column. A one-line action strip directly under the hero, full width, on every breakpoint.

4 · One title for every flight

FLIGHT n · number · DEP → ARR · date on every leg card, including a single-flight trip, so multi-flight duties scan identically.

1 · iPhone — compact (420 × 912)

One duty, two flights (PR501 / PR512, MNL–SIN–MNL). Crew markers are shown once on the duty card; each flight card carries only flight data. The calendar strip is full width under the hero. Scroll continues below Flight 2.

1
Paired times

SCHEDULED STD / STA, ESTIMATED ETD / ETA, ACTUAL ATD / ATA are three columns; departure and arrival stack inside each. Two text rows replace the three full-width rows, and block is a header chip.

2
Duty totals

Four KPI cells per duty: FDP, DP, Block, Rest. These are the portal’s own values (detailAll / report), not recomputed estimates.

3
Calendar strip

One-line, full-width action under the hero. On the Duo this is what frees the right column.

4
Consistent flight title

Every flight gets the same header: index, flight number, route, date (+ fleet). It no longer disappears on single-flight trips.

5
Markers on the duty

Wake-up / leave home / report belong to the duty. Later flights no longer repeat three “—” marker cells.

2 · iPhone Duo inner screen — wide (951 × 669)

Two-duty layover trip (TG662 BKK→PVG / TG663 PVG→BKK). Each duty is a horizontal group: the duty summary is sized to its content (292 pt), the flight card takes the remaining width. The rest strip separates duty 1 from duty 2. The 84 pt status/action strip on the right is preserved; the calendar no longer occupies a full right column.

3
Right column reclaimed

Previously the calendar card stretched across the right column with a large empty area. Now it is a 52 pt strip under the hero and the flight content gets the width.

4
Duty groups, not a flat leg list

DUTY 1 OF 2 and DUTY 2 OF 2 headers make it obvious when a new report/rest period starts. Flight numbering is continuous across the trip.

2
Rest between duties

The dashed strip shows the gap the portal reports as Rest Hours (05:49 arrival → 23:50 report = 18h 01m).

5
No empty marker cells

Duty 2 shows only the markers it actually has (hotel pick-up, report) — no “—” filler for wake-up or leave home.

3 · Six-sector duty — stress test (951 × 669)

The worst realistic duty: six flights on one report. The two-row time matrix keeps every sector card to ~138 pt, so four of six cards fit above the fold at 669 pt and rows 5–6 cost one short scroll. The shared-title table (Ver3) fits all six without scrolling — that is the trade-off between the two versions.

1
Two rows, three pairs

STD/STA, ETD/ETA, ATD/ATA are three columns; DEP and ARR stack inside each column. Six sectors add six short cards (~138 pt), not eighteen full-width rows.

2
Duty totals stay on top

FDP · DP · Block · Rest are reported once per duty, so they do not grow with the sector count.

4
Same title, six times

Every sector uses FLT n · number · route · block · fleet/date, so the list scans as a sequence.

5
Markers once

Wake-up / leave home / report are on the duty card only — the six sector cards never repeat them.

4 · iPhone Duo inner screen — tall (669 × 951)

Same TG trip, one column. Duty card and flight card stack; the duty card’s KPI cells stay on one row because the column is 541 pt wide. The layover hotel appears between the two duties, after the rest strip.

3
Same calendar position

Under the hero at every breakpoint — there is no separate “wide only” calendar layout to maintain.

2
Hotel in context

The hotel sits between duties, where the crew actually uses it, instead of after all flights.

5 · Calendar placement — before / after

The wide change is structural, not cosmetic: removing the calendar from the right column is what removes the empty right half.

Before — right column

Calendar card + large empty area; flight content squeezed into half the width.

After — full-width strip

Hero → calendar strip → duty groups use the full 809 pt content width.

6 · Data sources — no invented values

Everything shown in the frames exists in a captured payload or is directly derivable. The values in this mock are shaped like the portal’s own strings (HH:MM).

Implementation implication: portalCapture.ts must map the captured totals onto PortalDuty / Trip and persist them, because the raw report/detailAll payloads are not stored. For a carrier whose feed has no FDP/DP/Rest (the current F8/ET/EK mobile-roster API exposes only check-in/release + blockMinutes), the duty card should show Block and the duty span and omit the missing cells rather than display demo numbers. Airport ops values (boarding, door close, off-block, gate, stand, belt) remain explicitly demo until an A-CDM/AODB feed exists, as they are today.
